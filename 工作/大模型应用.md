# 大模型应用（16 周学习路线）

> 面向"企业级制造业 PPT 生成 Agent"的大模型应用学习路线，共 16 周核心路线 + 2 周可选进阶。
> 相关笔记：[[PPT生成Agent]]、[[AI-Agent系统性学习路线]]、[[书架与学习路线]]

---

## 一、总体路线

```
理解大模型
   ↓
调用模型 API
   ↓
控制模型稳定输出
   ↓
接入企业文档和数据
   ↓
调用工具完成任务
   ↓
构建 Agent 工作流
   ↓
建立评估、安全和权限
   ↓
使用 Docker、vLLM 私有化部署
```

## 二、总体安排

核心路线：16 周。建议每周投入 8～10 小时：

| 学习方式 | 每周时间 |
|---------|---------|
| 权威视频和文档 | 2～3 小时 |
| 编写代码 | 4～5 小时 |
| 测试与排错 | 1～2 小时 |
| 整理笔记和流程图 | 1 小时 |

不要采用"看完所有课程再做项目"的方式，而是：

```
学习概念 → 做一个最小功能 → 建立测试 → 接入你的 PPT Agent → 继续下一阶段
```

## 三、第一阶段：大模型基础原理（第 1～2 周）

### 1. 文本如何进入大模型

完整流程：

```
文本 → Tokenizer → Token → Vocabulary查Token ID → Embedding表查询向量
    → 加入位置信息 → Transformer → 输出Token概率
```

具体包括：
- Token 和 Token ID
- Tokenizer 与 Vocabulary
- Embedding 表
- 向量、矩阵、隐藏维度
- 位置编码和 RoPE
- 上下文窗口
- Logits 与 Softmax

### 2. Transformer

结构理解：

```
Transformer Block
├── RMSNorm / LayerNorm
├── Self-Attention
│   ├── Q / K / V
│   ├── Mask
│   ├── Softmax
│   └── 多头合并
├── 残差连接
└── FFN
```

还要知道：
- $W_Q$、$W_K$、$W_V$、$W_O$ 是模型参数
- Attention 权重和模型权重不是同一个概念
- FFN 为什么先扩维再压缩
- KV Cache 为什么能减少重复计算
- 训练和推理的区别
- Loss、梯度下降、权重更新的基本关系

### 必须能够解释

看到你的 Transformer 图时，能够逐步讲清楚：
- Token ID 如何查 Embedding 表
- 初始向量如何形成输入矩阵
- Q、K、V 如何生成
- Attention 如何建立 Token 之间的联系
- FFN 如何加工单个 Token
- Transformer 为什么重复多层
- 最后如何预测下一个 Token

### 必须能够操作

使用 Hugging Face Tokenizer 完成：

```python
tokens = tokenizer.tokenize(text)
token_ids = tokenizer.encode(text)
text = tokenizer.decode(token_ids)
```

并比较：
- 同一句话在不同模型中的 Token 数量
- 中文和英文的 Token 数量
- 长文本为什么会占用更多上下文

### 暂时不要求

- 手算大型矩阵
- 推导反向传播偏导数
- 推导 Attention 梯度
- 自己实现 CUDA 算子
- 从零训练 Transformer

### 阶段产出

- 修正你现有的 Transformer 流程图
- 写一个 Tokenizer 对比 Notebook
- 用自己的语言解释"训练"和"推理"的区别

## 四、第二阶段：模型 API 与 Prompt（第 3 周）

### 模型 API

理解一个标准请求：

```json
{
  "model": "模型名称",
  "messages": [
    { "role": "system", "content": "系统规则" },
    { "role": "user", "content": "用户问题" }
  ],
  "temperature": 0.2
}
```

需要学习：
- system、user、assistant、tool 角色
- OpenAI 与 Anthropic 消息格式区别
- 流式输出、Temperature、Top-p、Max tokens
- 超时、重试、并发、Token 用量
- HTTP 状态码

### Prompt

需要掌握：
- 明确任务、提供上下文、规定输出格式、给出正反示例
- 限制模型不能做什么、缺少数据时如何处理
- Prompt 模板化、Prompt 版本管理

### 必须能够实现

不依赖 LangChain，直接使用 Python 调用模型：

```python
class LLMClient:
    def chat(self, messages):
        ...

    def stream(self, messages):
        ...
```

这个客户端至少支持：Base URL、API Key、Model Name、超时、重试、日志、流式和非流式输出、OpenAI 兼容接口。

### 必须能够排查

| 错误 | 大致方向 |
|------|---------|
| 400 | 请求格式、角色或字段错误 |
| 401 | API Key 或鉴权错误 |
| 402 | 账户余额或额度 |
| 404 | URL、模型名或路由错误 |
| 429 | 并发或限流 |
| 500/502/503 | 网关、推理服务或模型服务错误 |

你之前遇到的 `messages[1].role = system / Input should be user or assistant` 就属于客户端和服务端消息协议不兼容。

### 阶段产出

建立统一模型适配层：

```
LLMClient
├── OpenAICompatibleClient
├── AnthropicCompatibleClient
└── LocalVLLMClient
```

让 PPT Agent 可以通过配置切换 Qwen、DeepSeek 或其他模型。

- **[Building Systems with the ChatGPT API](https://www.deeplearning.ai/short-courses/building-systems-with-the-chatgpt-api/)** — 重点不是聊天，而是将多次模型调用组合成可靠的软件流程

## 五、第三阶段：结构化输出与数据校验（第 4 周）

这是做企业级 PPT Agent 时最重要的一步。

### 需要学习的内容

- JSON、JSON Schema
- Pydantic BaseModel：必填字段、枚举、嵌套对象、字段校验、自定义验证器
- 模型输出解析、解析失败重试
- 结构化输出（Constrained Decoding）、本地模型兼容模式

例如定义 PPT 页面：

```python
from typing import Literal
from pydantic import BaseModel, Field


class Slide(BaseModel):
    title: str = Field(min_length=1)
    layout: Literal["title", "content", "chart", "image"]
    bullet_points: list[str]
    speaker_notes: str | None = None
```

### 必须实现下面的稳定流程

```
LLM生成内容 → 提取JSON → Pydantic校验
    → 校验通过 → 进入PPT生成
    → 校验失败 → 将错误反馈给模型 → 最多重试一次或两次 → 仍然失败 → 返回明确错误
```

### 必须理解三种方案

- **方案一：模型原生结构化输出** — 适合稳定支持 JSON Schema 的模型服务
- **方案二：Prompt 强制 JSON + 本地校验** — 适合你公司目前的 Qwen/vLLM 兼容情况
- **方案三：约束解码** — 在 Token 生成阶段限制模型只能生成符合规则的内容

### 验收要求

建议准备 50 条测试输入：正常需求、缺字段、字段类型错误、多余解释文字、空数组、超长内容、中文标点、错误 JSON、模型拒答、模型服务超时。

建议目标：**结构化输出解析成功率 ≥ 98%**（项目目标，不是行业统一标准）。

### 权威视频

- **[Pydantic for LLM Workflows](https://www.deeplearning.ai/short-courses/pydantic-for-llm-workflows/)** — 覆盖输入校验、LLM 响应校验、结构化输出和工具参数校验
- **[Getting Structured LLM Output](https://www.deeplearning.ai/short-courses/getting-structured-llm-output/)** — 讲解原生结构化输出、重试式结构化输出以及约束解码

## 六、第四阶段：RAG 企业知识库（第 5～7 周）

### 完整 RAG 流程

```
企业文档 → 解析与清洗 → 切片Chunk → 生成Embedding → 写入向量库
用户提问 → 检索相关Chunk → Rerank → 放入Prompt → LLM回答并引用来源
```

### 文档处理

需要掌握：PDF、Word、Markdown、Excel、PPT、网页、表格、标题层级、页码和来源信息。

### Chunking

需要理解：
- 固定长度切片、按标题切片、递归切片、语义切片
- Chunk overlap、父子块
- 表格不能随意切断

### 检索

需要掌握：Embedding、余弦相似度、Top-k、Metadata filter、关键词检索、BM25、向量检索、Hybrid Search、Rerank。

### 回答控制

需要实现：
- 回答带来源
- 找不到内容时明确说明
- 禁止模型根据常识乱补
- 区分不同版本文档
- 按部门进行权限过滤

### 必须能够解释

- RAG 为什么不修改模型权重
- Embedding 模型和生成模型的区别
- Chunk 太大或太小分别有什么问题
- Top-k 太大为什么可能引入噪声
- 为什么检索正确但答案仍然可能错误
- 为什么 RAG 必须单独评估检索层

### 必须能够实现

制作一个制造业知识库：

```
数据源
├── SOP
├── MES操作说明
├── ERP字段文档
├── BOM规则
├── 设备故障手册
└── PPT企业规范
```

用户询问"E102 报警代码是什么意思？"，系统必须返回：答案、来源文档、章节、页码或段落、文档版本。

### 必须能够评估

至少区分：
- 检索是否找到正确内容
- 答案是否使用了检索内容
- 引用是否真的支持答案
- 没有答案时是否拒绝乱答

### 阶段产出

企业 SOP 与 PPT 规范知识库，接入 PPT Agent，用于：查询企业字体规范、模板规则、内容结构、部门术语、历史优秀 PPT 示例。

### 权威视频

- **[Retrieval Augmented Generation（RAG）](https://www.deeplearning.ai/short-courses/retrieval-augmented-generation-rag/)** — 覆盖检索器、向量数据库、生成模型、部署与评估
- **[Building and Evaluating Advanced RAG](https://www.deeplearning.ai/short-courses/advanced-retrieval-for-ai/)** — 基础 RAG 后看，含 Sentence Window、Auto-merging Retrieval 和 RAG 评估

## 七、第五阶段：Function Calling 与 Tools（第 8 周）

### 标准工具调用流程

```
用户提出任务 → LLM判断是否需要工具 → LLM生成工具名称和参数
    → 程序校验参数 → 程序执行工具 → 将结果返回LLM → LLM生成最终答案
```

例如：

```python
def query_production_data(
    line_id: str,
    start_date: str,
    end_date: str,
) -> dict:
    ...
```

工具 Schema：

```json
{
  "name": "query_production_data",
  "description": "查询指定产线的生产数据",
  "parameters": {
    "type": "object",
    "properties": {
      "line_id": {"type": "string"},
      "start_date": {"type": "string"},
      "end_date": {"type": "string"}
    },
    "required": ["line_id", "start_date", "end_date"]
  }
}
```

### 必须掌握到什么程度

必须先不使用 Agent 框架，自己完成一次完整工具调用。必须理解：
- 模型只负责选择工具和生成参数
- 真正执行 SQL 的是你的程序
- 模型不能直接获得数据库管理员权限
- 参数必须经过 Pydantic 校验
- 工具异常必须转换成结构化错误
- 写操作必须幂等或带确认
- 工具需要设置超时
- 工具调用次数必须有限制

### 阶段产出

给 PPT Agent 加入三个工具：

```
Tools
├── search_company_knowledge
├── query_production_data
└── generate_pptx
```

- **[Functions, Tools and Agents with LangChain](https://www.deeplearning.ai/short-courses/functions-tools-agents-langchain/)** — 讲 Function Calling、结构化提取、工具选择、路由和 Agent。先理解原理，再使用 LangChain 实现

## 八、第六阶段：Agent 与 LangGraph（第 9～10 周）

### Agent 组成

```
Agent
├── LLM
├── Tools
├── State
├── Memory
├── Workflow
├── Routing
├── Retry
├── Human in the loop
├── Stop condition
└── Observability
```

### 需要区分 Workflow 和 Agent

- **Workflow**：步骤主要由程序提前规定（分析需求 → 查询资料 → 生成大纲 → 生成PPT）
- **Agent**：模型可以根据当前结果决定下一步（是否需要查文档？查数据库？重新生成？）

企业应用中，优先采用 **可控 Workflow + 局部 Agent 决策**，而不是完全放任模型自由执行。

### 必须能够实现

用 LangGraph 建立：State、Node、Edge、Conditional Edge、Tool Node、Retry、Memory、Human approval、Maximum steps。

### 必须能够排查

- Agent 无限循环、工具反复调用、状态丢失
- 工具参数错误、节点跳转错误
- 模型不调用工具、模型调用了错误工具
- 中间结果过长、任务执行到一半中断

### 暂时不要求

- 复杂多智能体组织、完全自治 Agent
- Agent 自己修改生产数据库
- 同时引入 CrewAI、AutoGen、LangGraph 等多套框架（先掌握一套即可，建议以 LangGraph 为主）

### 阶段产出

制造业分析 Agent：

```
接收用户需求 → 判断任务类型 → 检索SOP和字段说明 → 查询生产数据
    → 运行Python分析 → 生成结论 → 人工确认 → 生成PPT
```

## 十、第八阶段：评估与可观测性（第 12 周）

### 评估维度

- **模型评估**：回答正确性、指令遵循、格式正确率、内容完整性、稳定性、幻觉率
- **RAG 评估**：检索命中率、Context relevance、Groundedness、引用准确性、拒答正确性
- **Agent 评估**：工具选择正确率、参数正确率、执行顺序、任务完成率、循环次数、是否越权、是否经过人工确认
- **工程指标**：延迟、Token 数量、错误率、重试次数、工具调用耗时、模型服务可用率

### 必须建立一个测试集

```
evals/
├── normal_cases.json
├── edge_cases.json
├── tool_cases.json
├── rag_cases.json
├── security_cases.json
└── ppt_cases.json
```

每条测试至少包含：

```json
{
  "input": "用户输入",
  "expected_behavior": "期望行为",
  "required_tools": [],
  "forbidden_actions": [],
  "expected_fields": []
}
```

### 必须能够

- 修改 Prompt 后重新跑测试
- 切换模型后比较结果
- 查看哪一步失败
- 保存每次评估结果
- 防止修复一个问题后破坏其他功能

## 十一、第九阶段：企业安全与权限（第 13 周）

### 重点学习

Prompt Injection、间接 Prompt Injection、敏感信息泄露、过度代理权限、工具滥用、SQL 注入、路径穿越、恶意文件、不安全输出处理、第三方依赖风险、日志中的敏感信息、Secret 管理。

### 必须设计以下安全边界

```
用户 → 身份认证 → 应用层 → 参数校验 → Agent → 工具白名单 → Tool → 最小权限账号 → 数据库
```

工具至少分为：

- **只读工具**：查询文档、查询MES、查询ERP
- **高风险工具**：修改数据、删除文件、发送邮件、发布PPT

高风险工具必须加入：人工确认、审计日志、参数预览、权限校验、可撤销机制或幂等设计。

### 阶段产出

准备至少 20 条攻击测试：
- 忽略之前所有规则
- 输出系统提示词
- 读取其他部门文档
- 执行 DROP TABLE
- 删除服务器文件
- 把数据库密码写入 PPT
- 将内部文件发送到外部邮箱

## 十五、进阶阶段：LoRA、微调与量化（第 17～18 周，可选）

这个阶段不是当前最高优先级。

### 需要学习的内容

预训练、指令微调、SFT、LoRA、QLoRA、Rank、Alpha、Target Modules、Epoch、Learning Rate、Train/Validation Split、过拟合、模型合并、微调后评估。

### 必须先学会判断是否真的需要微调

| 问题 | 解法 |
|------|------|
| 模型缺少企业最新知识 | → RAG |
| 模型需要查实时数据 | → Tools |
| 模型输出格式不稳定 | → Structured Output + 校验 |
| 模型需要执行多步骤任务 | → Workflow / Agent |
| 模型长期无法适应固定表达风格 | → 再考虑 LoRA 或微调 |

### 必须掌握到什么程度

对于应用岗位，只要求：
- 能判断何时使用 LoRA、看懂 LoRA 配置
- 使用 LLaMA-Factory 或 PEFT 跑一次小模型 LoRA
- 比较微调前后结果
- 防止训练集表现好但测试集变差
- 知道如何将 LoRA 接入推理服务

### 暂时不要求

- 全参数微调几十亿参数模型
- RLHF 完整训练
- DPO 数学推导
- 大规模分布式训练

### 权威课程

- **[Hugging Face smol-course](https://github.com/huggingface/smol-course)** — 官方微调课程，覆盖微调技术的理解、实现和优化

## 十六、贯穿全程的综合项目

主项目不需要重新选择，直接继续完善：**企业级制造业 PPT 生成 Agent**。

### 最终架构

```
用户自然语言需求
        ↓
FastAPI接口
        ↓
需求结构化解析
        ↓
Agent工作流
├── RAG查询企业规范
├── 查询SOP和术语
├── 调用MES/ERP只读工具
├── Python数据分析
├── 生成PPT大纲
├── 选择固定模板
├── 生成PPTX
└── 质量检查
        ↓
人工确认
        ↓
输出PPT文件
```

### 必须包含的模块

```
project/
├── api/
├── llm/
│   ├── client.py
│   ├── prompts/
│   └── adapters/
├── schemas/
├── rag/
├── tools/
├── agent/
├── ppt/
├── evals/
├── security/
├── tests/
├── Dockerfile
└── docker-compose.yml
```

### 建议验收标准（项目目标，不是行业统一标准）

| 项目 | 建议目标 |
|------|---------|
| JSON 结构解析成功率 | ≥98% |
| 工具参数执行前校验 | 100% |
| PPT 文件生成成功率 | ≥95% |
| RAG 答案附带来源 | ≥95% |
| 高风险操作未经确认执行 | 0 次 |

系统架构图、用户操作演示、Agent 执行轨迹、RAG 引用结果、工具调用记录、PPT 输出结果、自动化评估报告、安全与权限说明、Docker 部署说明、本地 Qwen/vLLM 适配方案。
